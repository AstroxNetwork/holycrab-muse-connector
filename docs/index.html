Build a Muse connector in an afternoon

Muse is Meta's personal AI agent. It reaches third-party services through connectors. There is no app to register and no app id to collect — you expose an HTTP API that Muse reads about and calls. This guide takes you from an empty repo to a connector Muse can use.

Start the quickstart Browse the source

What you're building

Two files decide whether Muse can use your service: an OpenAPI document and an llms.txt. Muse reads both, then calls your API on the user's behalf.

/openapi.json

Machine-readable: what operations exist, what they take, what they return. Muse retrieves this to learn your API.

/llms.txt

The same thing in prose, plus the rules — when to ask the person first, and how to wait on slow work.

Per-connection tokens

Users get a scoped token, not your API key. Revocable, and the model never sees the real credential.

Muse ──(connector token)──▶ your connector ──(your credential)──▶ your API
        scoped, revocable      this template       held server-side

The output is a plain OpenAPI service. Muse reads it, but so can anything else that speaks OpenAPI — ChatGPT, Claude, Cursor, your own agent. Nothing here is Muse-specific except the wording conventions in llms.txt, and those are yours to change.

Quickstart

Five minutes to a running connector. You need Node 20+.

  1. Clone and install 
    git clone https://github.com/AstroxNetwork/muse-connector-template.git my-connector
cd my-connector
npm install
  2. Set three variables

    There are no defaults for PUBLIC_URL or DASHBOARD_URL on purpose — see Gotchas.

    cp .env.example .env

CONNECTOR_SECRET=$(openssl rand -base64 48)   # ≥32 chars
PUBLIC_URL=http://localhost:8787              # http is allowed for localhost
DASHBOARD_URL=https://example.com             # must be https
LINK_SECRET=dev-link-secret
  3. Run it 
    export $(grep -v '^#' .env | xargs)
npm run dev

    It prints a warning about missing KV. That's expected locally.

  4. Look at what Muse will see 
    curl -s localhost:8787/openapi.json | jq '.paths | keys'
# [ "/v1/me", "/v1/things", "/v1/jobs", "/v1/jobs/{id}" ]

curl -s localhost:8787/llms.txt

    Those four operations are placeholders. Read the llms.txt output carefully — everything you write into an operation ends up in there.

  5. Mint a token and call the API 
    TOKEN=$(curl -s -X POST localhost:8787/v1/link \
  -H 'content-type: application/json' \
  -H 'x-link-secret: dev-link-secret' \
  -d '{"subject":"you@example.com"}' | jq -r .token)

curl -s localhost:8787/v1/me -H "Authorization: Bearer $TOKEN" | jq

Run the tests. They are written as the specification, including the one that matters most: a retried paid operation must not create a second job.

npm test        # 50 tests
npm run typecheck

Make it yours

Three things to change. Everything else is plumbing.

1. Declare your capabilities

Open src/operations.registry.ts. Delete the three demo* operations and add one Operation per capability. That single entry generates the route, the OpenAPI path, the llms.txt line and the assistant's behavioural rules.

{
  id: "createVideo",              // stable; the model may cite it
  method: "post",
  path: "/v1/videos",
  summary: "Generate a video from a prompt",
  description: "Starts a generation. Returns a job to track.",
  input: { schema: z.object({ prompt: z.string().min(1).max(4000) }) },
  spends: { kind: "credits", note: "Costs 1 generation credit." },
  async: { pollWith: "getVideo", typicalSeconds: 90 },
  handler: ({ provider, connection, body, idempotencyKey }) =>
    provider.createVideo(connection, body as any, idempotencyKey),
}

Two fields are doing the heavy lifting. spends makes the description warn the model that this costs money. async points it at the operation to poll instead of resubmitting. Both are covered below.

2. Implement your service

Fill in src/providers/ against your real API. Delete placeholder.ts when you're done. The port is deliberately tiny to start:

export interface ProviderPort {
  whoami(connection: ConnectionRecord): Promise<WhoAmI>;
  // add one method per operation you declared above
}

Throw UpstreamError to control the HTTP status the caller sees — that is the only contract the rest of the connector relies on:

throw new UpstreamError(`no such job: ${id}`, 404);

3. Name it

SERVICE_NAME drives the OpenAPI title, /health and llms.txt. The package name and repo name are yours.

Async & paid work

This is where connectors go wrong, and it is almost never a code problem — it is a wording problem. Generation is asynchronous and costs the user money. If the model retries a POST to "check progress", the person is charged twice.

The double-charge failure mode. A slow operation plus an eager model equals a duplicate charge. Three things prevent it, and you need all three.

DefenceWhere
Mark it spends so the description says it costs moneyyour operation
Mark it async with pollWith so the model polls instead of resubmittingyour operation
Honour Idempotency-Key so a retry returns the same jobyour provider

Declare them once and they propagate into both documents:

spends: { kind: "credits", note: "Costs 1 generation credit." },
async: { pollWith: "getVideo", typicalSeconds: 90 },

The OpenAPI gains x-long-running, x-poll-operationId and x-requires-confirmation, and the generated description reads:

COSTS THE PERSON: Costs 1 generation credit. Do not call this until they
have agreed to this specific request. This returns immediately with a job to
track — poll `getVideo` (typically ready in about 90s). Do not resubmit to
"check" progress; that would create a second job.

And /llms.txt grows a section the model reads every session:

## Waiting on work
- `createVideo` returns a job; poll `getVideo` (about 90s).

Polling is free and safe. **Re-submitting is not** — it starts a second job.
A timeout is not a failure: keep polling the same job.

Say what a call will not do

Descriptions are read by a model deciding whether to act. "Reads your balance" is weaker than "Read-only. This cannot move funds." State the limit — it is what stops the model promising something you cannot do.

Deploy

Same source, three targets. No platform-specific code in the core.

Vercel

npm i -g vercel
vercel link
vercel env add CONNECTOR_SECRET
vercel env add PUBLIC_URL        # https://muse.your-domain.com
vercel env add DASHBOARD_URL     # https://your-domain.com
vercel env add KV_REST_API_URL   # Vercel KV or Upstash
vercel env add KV_REST_API_TOKEN
vercel deploy --prod

vercel.json rewrites every path to api/index.ts so your public URLs stay at the root. Muse must see https://muse.your-domain.com/openapi.json, not /api/openapi.json.

Cloudflare Workers

npm i -g wrangler
wrangler kv namespace create MUSE_KV   # uncomment kv_namespaces in wrangler.jsonc
wrangler secret put CONNECTOR_SECRET
npm run deploy:cf

wrangler.jsonc sets nodejs_compat, which is required because token signing uses node:crypto. Without it the Worker will not bundle.

Docker / any host

docker build -t muse-connector .
docker run -p 8787:8787 \
  -e CONNECTOR_SECRET=... \
  -e PUBLIC_URL=https://muse.your-domain.com \
  -e DASHBOARD_URL=https://your-domain.com \
  muse-connector

Persistence — do this before real users

Without a store, connections live in memory. Locally that is fine. On serverless it is not: each request may land in a fresh isolate, so users get logged out at random — and worse, a revocation only reaches one isolate. The service logs a warning when the binding is missing, on purpose.

StoreHow
Cloudflare KVbind MUSE_KV
Vercel KV / Upstashset KV_REST_API_URL + KV_REST_API_TOKEN
Anything elseimplement the four-method ConnectionStore interface

Switching is automatic: if KV is configured, it is used.

Gotchas

Why are PUBLIC_URL and DASHBOARD_URL required?

They are not decoration. PUBLIC_URL becomes the OpenAPI servers entry — the address Muse is told to call. DASHBOARD_URL is printed to users as the place to revoke access. A default would mean a half-configured deploy tells Muse to call, and sends users to, the wrong site. So the connector refuses to start instead.

Do I need a subdomain?

No. Any public HTTPS URL works — a subdomain, a path on your main domain, or a *.workers.dev URL while testing. A subdomain is a good habit because your main site probably already owns /llms.txt and /openapi.json, and its WAF may treat API traffic as bot traffic.

Does this need MCP?

No. Muse's custom connectors work over plain REST plus an OpenAPI document. MCP is a different protocol and a different product (Muse Code, the CLI).

What if the model calls something at the wrong time?

Every call goes through Meta's permission layer, which can allow, deny, or ask the user. Your job is to make the request legible: a clear summary, an honest description, and a spends note when it costs something.

Can I use this without Muse at all?

Yes. It is an authenticated OpenAPI service with a token-minting endpoint. Point any agent at it.

Is it really Apache-2.0?

Yes. Fork it, rename it, strip the branding. Keep the NOTICE file for the files you redistribute; your deployed service does not need to credit anyone.
